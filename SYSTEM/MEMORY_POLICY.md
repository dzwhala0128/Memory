# 跨会话记忆协议｜Memory Policy

**生效背景：** 用户在2026-11-06明确要求建立分类记忆仓库，并授权后续科研对话中对重要进展主动写入GitHub。  
**生效范围：** 可访问本仓库并已读取本文件的助理会话。仓库规则不能超越平台系统规则，也不能在未运行的会话外自行执行。

## A. 分类与命名规则

- `SYSTEM/`：跨项目协作规范、记忆维护规则、新会话入口。不放任何HerO实验结果。
- `PROJECTS/README.md`：注册独立项目的索引；各项目内容只放在自己的项目目录。\n- `TOPICS/README.md`：记录不依附某个具体项目的非私人主题，如通用技术知识、工具经验等。
- `PROJECTS/HERO/`：只存HerO × TextGrad相关研究、当前Final项目、实验记录、工作台对齐等。
- 新的**其他科研项目或工作项目**：`PROJECTS/<PROJECT_ID>/`；每个项目拥有自己的 `README.md` 与专题文档。
- 不应将不同领域的模型结果/运行脚本交叉粘贴。共有规范由SYSTEM统一解释；各项目细节由项目目录独立维护。

## B. 主动同步：已授权的默认行为

在**本会话可以调用GitHub且写入权限有效**时，遇到下列已完成、可验证的科研事项，**无需再次逐项询问授权**，主动提交到匹配的项目记忆文件：

1. 完成重要实验、获得有意义的输出/指标/错误诊断，记录实验ID与数据规模。
2. 改变研究假设、方法设计、金标签隔离、算法职责或明确否决某条方案。
3. 更新代码主入口、实际模型、提示词、Few-shot配置、数据目录和依赖关系。
4. 完成重要复现验证/失败分析、做出影响后续操作的决策。
5. 重要的下一阶段计划被用户明确确定；标记“计划中”，不冒充已实施。

**暂不提交**：闲聊、未核实推测、重复问答、纯临时命令排版、用户明确说不需要保存的事项。

**写入步骤（助手内部执行标准）**：
- 阅读对应现有记忆及最新代码/实际日志（在可访问情况下）。
- 核对证据，把“用户报告”“静态核实”“实际运行”“待验证”区分开。
- 只改对应领域文件，必要时更新索引和更新时间；不覆盖历史证据。
- 提交到GitHub后读取或核对文件，并在回复中附上链接和同步状态。
- 无GitHub连接、网络或写入权限时如实告知；**不得宣称已经同步，也不应暗中以后补做**。

## C. 新会话如何执行

- 当新会话已经获知本仓库时，应先阅读 `README.md` 与本规则，再读取当前任务的 `PROJECTS/<ID>/README.md`。
- 新会话在参与相关科研任务时，遵守B节“主动同步”协议；可在完成重要进展的当次回复内写入，减少用户重复提醒。
- **技术限制**：仓库文本不会自动加载到未触达仓库的新会话里，不能保证新窗口“无需提示就自己读取、自己提交”。若希望每次新会话都有触发条件，用户可把 `SYSTEM/SESSION_BOOTSTRAP.md` 的短指令加入 ChatGPT 的自定义指令；自定义指令是否被遵守、外部GitHub是否可用仍取决于该会话能力。
- 不启用无明确授权的定时后台写入；不自动扫描全部历史聊天。

## D. 事实与安全边界

1. **只保存公开安全的科研/工作信息**；不上传私生活、身份信息、服务器账号路径、API密钥、SSH私钥、Token、代理/隧道密码、未脱敏日志。
2. 本仓库当前公开；若将来更改为私有，也不把秘密写入Git历史。
3. **最新可验证的实际代码与输出优先于记忆摘要**。项目代码尚未同步时，不能把其他GitHub仓库冒充其最新镜像。
4. 过去的指标要带来源和实验条件，不能嫁接到最新开发版本。
5. 新结论推翻旧结论时，解释证据与版本差异，不进行无标记覆写。
6. 用户可以随时修改规则或暂停某个项目的自动同步。

## E. 文件职责与冲突处理

- 规则冲突：`SYSTEM/MEMORY_POLICY.md` 提供仓库默认规范；具体项目文件不得擅自覆盖隐私边界。
- 项目事实冲突：以同一仓库/分支最新源码和可复现实验输出为准；必要时记录两者的时间与不确定性。
- 用户明确的最新项目范围优先于旧摘要。当前HerO工作项目为 `Final`；不要在系统规则中嵌入其他具体代码项目名称或旧路径。
- 不确定信息标注 `待验证`，不要为了让记忆显得完整而自行补全。

## F. 维护周期与质量

- 完成一轮重要任务即可做一次有选择的增量更新，无需每条消息提交。
- 避免重复文档；README索引，项目首页摘要，专题保留可核实细节。
- 记录变更日期（时区）、相关GitHub链接/运行ID/版本，以及是否从用户终端输出确认。
